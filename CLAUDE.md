# PointPal

A multi-child, installable PWA for tracking kids' activities (chores) and earned screen time/prizes, with a parent-gated approval flow. Supabase-backed (Postgres + Auth + Realtime) for cross-device sync — one shared family login across multiple kiosk tablets. No offline-first fallback: the app requires a live connection to boot and to make any change.

## What it does

- **Child side (per-child view; switching to another child requires that child's own PIN — see Security below):**
  - Tap activity cards to request credit — each activity earns either points or minutes (`currency`), per its own setting. Activities can be repeatable, one-time-per-day, or follow a recurring/one-time **schedule** (daily / certain weekdays / every-other-week / monthly / one-time-only). Drag the ⠿ handle on an activity or prize row (Parent Zone) to reorder — that order is what Home/Prizes actually render.
  - Browse a **Prizes** tab and request redemptions (spends points). A prize can optionally cap redemptions per day/week (`limitMax`/`limitPeriod`), optionally grant minutes on delivery (`grantsMinutes` — see fulfillment tracking below), and a child can pin one prize as a **savings goal**, shown as a progress bar on Home.
  - View a chronological **History** tab (by week or month) of everything requested/approved/denied, including per-entry fulfillment/minutes-used status where relevant.
  - A header meter pair shows current points and screen-time minutes as two large, high-visibility numbers, each backed by Pip artwork in its own color story (a treasure chest for points, Pip watching TV for screen time) — plus the child's own avatar next to their name. This replaced an earlier "tank" motif (a filling water tank with animated fish/bubbles), fully retired in favor of leaning on Pip everywhere — see the Pip mascot section below.
  - Home shows, top to bottom when applicable: a savings-goal progress bar (Goal Pip), **Active Punishments** (Pause Pip), **Active Challenges** (Streak Pip), then the activity grid.
  - The child doesn't see celebration confetti/animations at approval time — those are queued and delivered the next time *that child's own session* becomes active, framed as a message from Pip. See "Pip notifications" below.
- **Parent side (PIN-gated, default family PIN `1234`; 5-attempt lockout with a 30s cooldown, shared across every PIN attempt — parent or any child):**
  - **Approvals** tab: approve/deny any pending entry, bulk-approve all, 6-second undo toast on a single approve/deny. A second section below lists approved redemptions still awaiting a **Mark Delivered** tap (see fulfillment tracking).
  - **Activities** tab: edit label/icon/schedule/repeatable/amount/currency, delete, add activities, or drag to reorder.
  - **Prizes** tab: edit costs/icons/optional minutes-granted, delete, add prizes, or drag to reorder; set an optional redemption limit via a picker pill (no limit / N per day / N per week).
  - **Challenges** tab: create/edit/remove challenges — each watches one activity's approvals and pays a bonus (points or minutes) once a target count is hit, either **recurring** (resets weekly, indefinite) or **one-time** (only active between an explicit start/end date; pays out once, then simply stops appearing once the end date passes, completed or not).
  - **Punishments** tab: create/edit/remove temporary blocks — each can block point-earning activities, minute-earning activities, and/or prize redemption (any combination), for a set duration (hours or days). Blocked activities/prizes show visibly dimmed to the child; blocks lift automatically on expiry or can be removed early, and either way the child gets a Comeback Pip notification once it lifts (see Pip notifications).
  - **Settings** tab (Profile / Points & Time / Manual Entries / Message / Voice Lines / Data sub-tabs): rename/add/remove children, pick each child's **avatar** and set their **PIN**, change the family PIN; adjust points/minutes and log partial screen-time usage (FIFO across a child's earned-minutes entries — see fulfillment tracking); backfill past activity/prize entries (dated in the past, credited immediately, no approval needed); write a custom **Message** for a child, delivered the same way as a celebration; manage Pip's voice lines (see "Pip voice lines" below); **Data** sub-tab: "Edit Individual Entries" lists a child's own entries newest-first (filterable by Activities/Prizes/Bonuses) with per-entry **Unapprove** (reverts to pending, reversing its balance effect) and **Delete** (removes it outright, also reversing the balance if it was approved) — the one sanctioned exception to "nothing is deleted from entries," meant for correcting an outright mistake rather than routine editing; below that, reset a child's data entirely (preserves that child's avatar, PIN, *and* their whole activity/prize/challenge catalog — only points/minutes/history/punishments clear).
- Every child-initiated request creates a `pending` entry; nothing affects the point/minute balance until a parent approves it (manual backfills in Settings are the one exception — they apply immediately).
- "Good Day at School" is **not** special-cased in code — it's an ordinary seeded activity (`id:'school'` pre-migration / a fresh `uid()` for any child created after the Add Child fix below, worth 15 min) plus a seeded recurring Challenge that reproduces the old hardcoded streak. Both are fully editable/removable through the normal Activities/Challenges tabs, same as anything a parent adds later.

## Security: avatars, per-child PINs, and the kiosk idle-lock

- Each child has a picked-from-a-set emoji `avatar` (`AVATAR_SET` in `app.js`, themed around dinosaurs/construction/sloths/space/science/ninjas/superheroes/gaming) and their own 4-digit `pin`, both editable in Parent Zone → Settings → Profile. New children default to a rotating avatar and the current family PIN; a data reset preserves both.
- **Every** child switch — via the Home child-switcher pills or the lock screen below — routes through the PIN pad and compares against that specific child's PIN (falling back to the family PIN if a child's own is somehow unset), **unless a parent session is already active** (see below). `pinContext` is `{type:'parent'}` or `{type:'child', childId}`; `pressPinKey`'s success branch checks the right PIN and either calls `switchChild()` or `openParent()`.
- A single global **30-second idle timer** (`APP_IDLE_MS`, `startAppIdleWatch()`) runs for the whole app session (started once from `afterAuth()`, never stopped). After 30s of no click/input/touch anywhere, it closes any open overlay and shows a full-screen animated lock screen (`#kioskLockScreen` — see "Lock screen" below) with one large avatar tile per child plus a "Parent" tile — tapping a tile opens the PIN pad for that child or the family PIN; success hides the lock screen and either switches child or opens Parent Zone directly. The same lock screen also appears manually via the 🚪 exit-profile button in the header (calls `showLockScreen()` directly — identical to an idle timeout) and once at the end of every `afterAuth()` run (fresh login or cold boot), instead of landing straight on whichever child was last active — see "Pip notifications" below for why.
- **`parentSessionActive`** (a module-level flag, set in `openParent()`, cleared in `showLockScreen()`) means "a parent PIN was accepted and the lock screen hasn't reappeared since." While true: the header lock icon re-opens Parent Zone directly instead of re-prompting for the PIN, and tapping another child's pill in the Home child-switcher calls `switchChild(id, {viaParentSession:true})` directly instead of going through that child's PIN pad — letting a parent hop between kids' Activities/Prizes/Settings without re-authenticating for each one. It's deliberately scoped to the in-app switcher only, **not** the lock screen's own tiles, which always still require a PIN — the lock screen itself is what ends a parent session in the first place. The `{viaParentSession:true}` flag on `switchChild()` also suppresses arming `notificationsArmed` (see "Pip notifications" below) — a parent-driven switch is still the parent looking at the screen, not that child, so it must not deliver that child's queued Pip moment.
- The PIN pad (`#pinOverlay`) is deliberately given a higher z-index (1200) than everything else including the lock screen (1000), so it always layers on top and Cancel naturally reveals whatever was underneath — the lock screen if idle-triggered, or the already-unlocked app if opened manually via the header lock icon.

## Pip mascot system

PointPal has a full mascot, **Pip**, with a named creative brief (kept as `Creative Brief.txt` in the project folder, not checked in) covering personality, a glowing chest "Point Core" symbol, a Sparks/Spark-Trail visual language, and named expression states. The user supplies art as PNGs dropped into the project root; Claude renames each to a clean, purpose-based filename before wiring it in (`pip-<pose>.png` for character poses, `nav-<name>.png` for nav bar icons, `badge-<name>.png` for small UI badges) and leaves the user's original-named files untouched/untracked.

**Before wiring in any new art, verify it has real alpha transparency** — inspect via .NET `System.Drawing.Bitmap` in PowerShell (`$img.PixelFormat` should be `Format32bppArgb`, and a corner pixel should read `A=0`). Several assets this project has received looked transparent (a checkerboard pattern) but were actually `Format24bppRgb` with the checkerboard baked in as opaque pixels — a common export mistake. Re-export is the fix; don't try to algorithmically strip a baked-in checkerboard.

**Card styling pattern** (established across the Points/Screen-Time meter cards, reuse for future Pip integrations): a `background: linear-gradient(...)` pulled from that specific artwork's own palette, scoped to the element's own id/class; the Pip image anchored `position:absolute; left:8px; bottom:-14px;` at roughly the card's own height, intentionally bleeding a little past the bottom edge (parent needs `overflow:hidden`); and the label/value text `justify-content:flex-end; text-align:right;` so Pip has room and isn't fighting the numbers for space.

**Current pose inventory** (`pip-*.png`): `wave` (generic hello, the lock screen's default), `celebration` (arms up, confetti — approval celebrations), `streak` (running, spark trail, goggles — Active Challenge cards and the lock screen when a child has real challenge progress), `goal` (telescope — savings-goal card), `pause` (calm, beside a dimmed chest — Punishment cards and the lock screen during an active punishment), `comeback` (holding a lantern — delivered when a punishment lifts), `message` (a.k.a. "Ready Pip", holding a coin — custom parent messages), `tv` (watching TV, popcorn — Screen Time card), `treasure` (tossing a coin into a chest — Points card), `flying` (mid-flight with his own star trail — alternates with `wave` as the lock screen's no-special-state pose), and the standalone `point-core` symbol (small icon next to the Points label/value, and on lock-tile stat rows). `point-core-spark` is a separate, sparklier variant of that same symbol used only as the flying-coin sprite in the coin-shower animation (see "Juicy approval feedback" below) — not a swap-in replacement for the plain `point-core` icon elsewhere.

## Pip notifications (queued celebrations, delivered to the child)

Approving an entry no longer bursts confetti at whoever's tapping Approve in Parent Zone — that's almost always the parent, not the kid who earned it. Instead, `approveEntry()` queues a **notification** (`kind:'celebration'`) for the child, persisted to a dedicated `notifications` table, and it's delivered as a Pip-voiced modal (`#pipNotifyOverlay`, shown via `showNextNotification()`) the next time *that specific child's own session* becomes active — not the instant it's approved. Denials never queue a notification; per the brand brief, Pip never delivers bad news.

- **Delivery hook points**: `switchChild()` (a genuine PIN entry into that child's session — the realistic "kid picks the tablet back up" moment, since the 30s idle-lock makes this fire constantly), `afterAuth()` (cold boot / fresh login), and `scheduleRefetch()`'s realtime-triggered success path (covers a kid already actively using the app live when something gets approved from another device) — each guarded by `deliverPendingNotifications()`, which no-ops if the kiosk is idle-locked, Parent Zone is open, or **`notificationsArmed` is false**. **Deliberately not hooked into `closeParent()`** — that fires right after the parent approves something, so showing it there is the exact bug this system exists to fix (the parent sees it again, not the kid).
- **`notificationsArmed`** (a module-level flag, near `kioskLocked`) exists because `child` just means "whichever child was last active on this device," not "who's actually looking at the screen right now" — a parent logging in, or closing Parent Zone, lands back on that stale child's Home, and without this flag `scheduleRefetch()`'s realtime path would deliver that child's queued Pip moment to the parent instead. It's only set `true` inside `switchChild()` when called from a successful *child*-PIN entry (never a parent one, and never a `{viaParentSession:true}` switch — see `parentSessionActive` in the Security section above), and reset to `false` by `showLockScreen()`, `openParent()`, and at the top of every `afterAuth()` run — i.e. it's true only in the window between a genuine child PIN unlock and the next lock/parent-entry/login.
- `afterAuth()` always ends by calling `showLockScreen()` rather than rendering straight into the last-active child's Home — both on a fresh login and on a cold boot/reload of an existing session. This is the other half of the same fix: logging in as the parent no longer exposes whatever child was last active on that device, PIN pad included.
- **Kinds**: `celebration` (a plain chore or redemption approval — redemption-vs-chore is told apart the same way the voice line is, by `n.currency` truthy/falsy), `streak` (auto-queued instead of `celebration` when the approved entry is a challenge-bonus entry — `e.kind==='bonus'` — so a challenge win gets `pip-streak.png`/confetti/the `streak` voice bank instead of the generic chore treatment), `goal` (queued by `maybeQueueGoalProgress()`, see below), `message` (parent-authored, via Settings → Message), `comeback` (queued by `notifyPunishmentExpired()` whenever a punishment lifts, whether by natural expiry — `schedulePunishmentExpiry()` — or early manual removal). A comeback notification uses a deterministic id (`comeback-<punishmentId>`) so if more than one kiosk has the same child active and each schedules its own expiry timer, only the first insert wins; the rest hit a Postgres unique-violation (`error.code==='23505'`) that's swallowed intentionally, not treated as a sync error.
- **`maybeQueueGoalProgress(c, pointsBefore, e)`** (called from `approveEntry()`, right after crediting) queues a `goal` notification when a points-earning approval pushes the child's pinned savings goal (`c.goalPrizeId`) across a 25% boundary — 25/50/75/100, computed via `goalProgressPct()`, comparing the before/after percentage so it fires once per boundary crossed rather than on every approval. Deliberately one-directional: skipped entirely for `redeem` entries and for minutes-currency chores, since a *drop* in progress (points spent elsewhere) should never surface as a Pip moment — only forward progress does, matching the brief's "Pip only encourages, never flags a setback" rule that already governs Punishments.
- Dismissing (`dismissNotification()`) deletes the row outright — there's no "seen" history to keep, `notifications` is purely a delivery queue.

## Pip voice lines (`app.js`, "PIP VOICE LINES" section, just above "PIP NOTIFICATIONS")

`playPipVoice(moment)` plays a short, randomly-assembled Pip voice line — `moment` is one of `'points'`, `'minutes'`, `'redeem'`, `'comeback'`, `'goal'`, `'streak'` — and **returns the exact transcript of what it just played** (or `null` if nothing's recorded for that moment) — called from `showNextNotification()`, which prepends that returned text onto the notification's usual body text, so the displayed words and the spoken words can never drift out of sync with each other (there's no second, independently-written "what Pip says" string anywhere). A plain chore approval picks `'points'` vs `'minutes'` by `n.currency`; a redemption uses `'redeem'`; a challenge-bonus approval (notification `kind:'streak'`) uses `'streak'`; a savings-goal boundary crossing (`kind:'goal'`) uses `'goal'`.
- Each bank entry is a **`{file, text}`** pair, not a bare filename — `text` is the single source of truth for both what plays and what's shown. A call mixes up to four entries end-to-end (`playClipSequence()`, chained on the `ended` event with a `PIP_VOICE_GAP_MS` pause between): an optional **name** clip (see below), a generic **opener** (`PIP_VOICE_OPENERS`), a moment-specific **contextual** entry (`PIP_VOICE_CONTEXT[moment]`, the only part that actually says anything specific), and a generic **closer** (`PIP_VOICE_CLOSERS`) — openers/closers are reused across every moment so a small recorded set produces many distinct-sounding combinations, and each is only ~70% (`PIP_VOICE_BEAT_CHANCE`) likely to play at all.
- **Name clips** (`PIP_VOICE_NAMES`, category `'name'`) are matched to whichever child is currently active by comparing the clip's own `text` to `child.name` (case/whitespace-insensitive — `pickNameClip()`), not by a moment key, since a name clip belongs to one specific kid rather than a kind of event; recording more than one clip with the same name (e.g. two different takes) is supported, one is picked at random. It always plays *first*, ahead of the opener, and is deliberately not subject to `PIP_VOICE_BEAT_CHANCE` — it either plays or not, gated instead by whether it's already been *attempted* this batch (see below).
- **At most one name and one opener per notification batch, not per notification** — `pipNameAnnounced`/`pipOpenerPlayed` are module flags that go `true` the first time either beat is *attempted* in `playPipVoice()`, whether or not that attempt actually produced a clip (a failed 70% opener roll still counts — it's one roll of the dice per batch, not a retry on every queued item). Both reset to `false` only in `deliverPendingNotifications()`, right before a fresh `showNextNotification()` call actually starts a batch — **not** in `dismissNotification()`'s call to show the next item in an already-running queue, which is exactly what keeps a run of several notifications in one sitting from re-rolling either beat for every single one. The **closer** needs no equivalent flag — it's gated on `child.notifications.length<=1` (this is the last item still in the queue at call time) instead of a "have I already gone" flag, which by construction only one notification in a given batch ever satisfies.
- **Fully self-service, no code changes needed to add a line.** The banks are never hand-edited — `rebuildVoiceBanks()` rebuilds them from `state.voiceLines`, which is the `pip_voice_lines` Supabase table (migration: `migration_pip_voice_lines.sql`, columns `category`/`file`/`phrase`), managed entirely from **Parent Zone → Settings → Voice Lines** (`settingsVoiceLinesHTML()`). The actual audio *bytes* are distributed the same way every other project asset already is — the user drops a file into the repo's `voices/` folder and pushes to GitHub, which is also what deploys the live site, so there's no separate sync step. The admin tab's file-picker `<select>` is populated by `fetchVoiceFileOptions()`, which calls GitHub's public, unauthenticated Contents API (`api.github.com/repos/cullie140/PointPal/contents/voices` — the repo is public, no token needed) to list whatever's currently in that folder; it's cached per session and re-fetched on the tab's "Refresh file list" button. This listing call only feeds the admin picker — actual child-facing playback in `playClipSequence()` just fetches `voices/<file>` same-origin, no GitHub API involved, so it has no dependency on GitHub's API uptime or rate limit.
- No `sw.js` `ASSETS` changes are needed when new voice files are added — that array is only the install-time precache warm-up; `sw.js`'s generic `fetch` handler already cache-first-caches *any* same-origin GET the first time it's requested, `voices/*` included.
- Deliberately **not** wired into the `message` notification kind (a generic clip under a parent's own custom-authored text would feel mismatched) or into `punishments` activating (per the brief, Pip never delivers the restriction itself — only the `comeback` moment when it lifts).
- Record openers and closers in the same session/voice settings as each other — since any opener can land next to any closer, a mismatch in recording energy is what would make the illusion fall apart, more than word choice would.

## Juicy approval feedback (`app.js`, right after `burstConfetti()`)

`flyRewardPieces(amount, originRect, destEl, buildPiece)` is the shared engine — it computes origin (from `originRect`) and destination (`destEl.getBoundingClientRect()`) screen coordinates once, then runs the staggered per-piece launch loop (`REWARD_FLY_STAGGER_MS` apart, capped at `REWARD_FLY_MAX` (10) pieces regardless of the actual amount — a +120 min challenge bonus shouldn't mean waiting through 120 individual pieces), calling `buildPiece(sx, sy, dx, dy, isLast)` to actually create and animate each one. The two reward types differ only in what `buildPiece` does:
- **`flyCoinsToMeter(amount, originRect)`** — points, into `#pointsMeter`'s `.point-core-icon`. Each `pip-point-core-spark.png` copy spins (`rotate()`, not 3D `rotateY` — the sprite is flat, so a real Z-axis cartwheel reads as "spinning" without needing a second back-face image) and shrinks (`scale(1)`→`scale(0.3)`) along a slight rise-then-fall toss arc, with a landing clink (`playCoinLandSfx()`, `sfx-coin-land.wav`) on *every* coin — overlapping rapid clinks as they land in succession is what sells "a shower of coins" rather than one dull thud.
- **`flySparksToMeter(amount, originRect)`** — minutes, into `#minutesMeter`'s `#minutesVal`. No dedicated minutes icon/art exists, so each piece is just a CSS-drawn `✨` (`.spark-fly`, with a cool-blue `drop-shadow` matching the Screen Time card's own palette, vs. the coin's gold) — no spin, a flatter/quicker arc than the coin's toss, and a fade instead of a hard cutoff. Landing sound: `playScreenTimeLandSfx()` plays `sfx-screentime-land.wav` on every spark, same "every landing gets a sound" treatment as the coins.
- Both use the Web Animations API (`element.animate()`) rather than a static CSS `@keyframes` class, specifically because both endpoints are computed per-call from live layout, not fixed.
- **Fires once per notification, on dismiss** — `dismissNotification()` calls whichever one matches the dismissed notification's `n.currency` (`'points'`/`'minutes'`, on a `celebration`/`streak` kind), every time, not just when the queue finally drains to empty. `originRect` is `#pipNotifyImg`'s `getBoundingClientRect()`, captured at the very top of `dismissNotification()` — *before* the current modal starts closing or (if more are queued) swapping to the next notification's Pip pose — so the pieces launch from wherever Pip was actually standing for *that specific* notification, not a fixed screen position. (Name/opener/closer above still batch across a whole run of notifications — that's about not re-rolling the same generic voice beats repeatedly, a different concern from where each individual reward's pieces fly from.)
- **The modal is held open until every piece has launched**, not closed instantly on tap — `dismissNotification()` awaits `(count-1)*REWARD_FLY_STAGGER_MS + REWARD_FLY_LAUNCH_HOLD_MS` before actually swapping/closing, where `count` is the same `Math.min(n.amount, REWARD_FLY_MAX)` `flyRewardPieces()` itself computes. This only waits for the *launches*, not full landings — pieces keep flying toward the meter after the modal closes regardless, since they live on `#floaters`, a layer independent of the notification overlay. Without this, the modal (and Pip's image with it) vanished before the pieces had visibly left him, since `#floaters` renders above everything regardless of the overlay's own state.
- **Meter pulse**: `pulseMeterCard()` fires only once per dismissal, timed to the *last* piece's `animate().onfinish` (the `isLast` flag `flyRewardPieces()` passes to `buildPiece`) — not once per piece, which would stack jittery back-to-back scale transforms on the same element instead of one clean confirming "thunk."
- Unlike the optional, admin-managed voice-line clips in `voices/`, `pip-point-core-spark.png`, `sfx-coin-land.wav`, and `sfx-screentime-land.wav` are core always-present assets checked into the repo root like any other `pip-*`/`badge-*` file, and **are** listed in `sw.js`'s `ASSETS` precache array — the "don't add a file to `ASSETS` before it exists" landmine documented under Pip voice lines applies only to the dynamic voice system, not to fixed assets like these that ship in the same commit as the code referencing them.

## Lock screen (`#kioskLockScreen`)

An animated night-sky scene, not a static gradient: a twinkling star field and a slow rising-sparkle drift (both pure CSS via layered `radial-gradient`s — no image assets), a rotating Pip-voiced tagline (`LOCK_TAGLINES`, cycled by `startLockTagline()`/`stopLockTagline()`, started/stopped alongside `showLockScreen()`/`hideLockScreen()`), and each child's tile showing their live points/minutes plus a bouncing mail-badge (`badge-mail.png`) if they have unseen Pip notifications waiting — so a parent or kid can see who's got something without unlocking. Tiles pop in with a staggered entrance animation on each render. The PointPal wordmark logo is pinned to the top of the screen (`#kioskLockScreen{justify-content:flex-start}`) rather than vertically centered with everything else — on a tall tablet viewport, centering the whole block left a lot of dead space above the logo; a `.lock-body` wrapper now centers Pip/tagline/tiles in whatever space is left below the fixed logo.

The big central Pip's pose is picked by `pickLockScreenPip()`, in priority order: any child has an unseen celebration/comeback waiting → `pip-celebration.png`; any child is under an active punishment → `pip-pause.png`; any child has real progress on an active challenge → `pip-streak.png`; otherwise a 50/50 random pick between `pip-wave.png` and `pip-flying.png`. Deliberately *not* every pose in the inventory gets a lock-screen slot — three simultaneous Pips (greeting + a background flyby + tile-level context) was tried and read as too busy; the flying pose was folded into the main rotation instead of being its own animated background layer.

## File structure

Flat, no build step, no dependencies:

- `index.html` — all markup + all CSS (custom properties for the color theme, no framework). Shell (header/meters, nav bar, child-switch row, PIN overlay, Parent Zone overlay, icon/schedule/challenge/punishment/limit picker overlays, offline banner, boot/login screens, kiosk lock screen) plus an empty `#mainContent` div that `app.js` fills per view. Loads the Supabase JS CDN script before `app.js`.
- `app.js` — the entire application: Supabase client + sync, multi-child state, business logic, and hand-rolled DOM rendering (HTML strings via template literals, re-rendered wholesale on `render()`).
- `manifest.json` — PWA manifest (name, icons, theme colors, `orientation:"any"` for tablet landscape/portrait).
- `sw.js` — service worker: cache-first-with-background-refresh for the app shell only (`CACHE_NAME` = `pointpal-cache-vNN`; explicitly ignores cross-origin requests so it never intercepts Supabase traffic). **Bump `CACHE_NAME` on every shipped change** — a stale SW cache masking edits is the most common "why isn't my change showing up" during local testing; the fix is unregister service worker + clear caches + hard reload.
- `icon-192-v2.png`, `icon-512-v2.png` — favicon + web app manifest icons (renamed with a version suffix once already, to force iOS to drop its stubborn home-screen-icon cache — bump the suffix again if the icon ever needs to change and a cache-stuck report comes back).
- `apple-touch-icon-180.png` — the iOS-specific Home Screen icon, referenced via `<link rel="apple-touch-icon" sizes="180x180">`. Kept as a separate file/size from `icon-192-v2.png` because iOS ignores the manifest entirely for "Add to Home Screen" and is picky about getting an exact-sized, fully opaque (no alpha) square at Apple's own recommended 180×180 — a same-but-different-size icon reportedly got silently padded with white and shrunk.
- `logo-horizontal.png` — the Pip + wordmark lockup used on the boot/login/lock screens.
- `pip-*.png`, `nav-*.png`, `badge-*.png` — the Pip mascot art system; see "Pip mascot system" above for the full inventory and the transparency-verification step to run before wiring in a new one.

## Data model — Supabase, not localStorage

Postgres tables, each with `user_id uuid default auth.uid()` + RLS policy `user_id = auth.uid()`. One family = one `auth.users` account, shared across all kiosks.

- `children` — `{id, user_id, name, avatar, pin, points, minutes, week_start, goal_prize_id}`
- `chores` — `{id, child_id, user_id, label, emoji, amount, currency:'points'|'minutes', repeatable, schedule jsonb, sort_order}` — the activity catalog
- `prizes` — `{id, child_id, user_id, label, emoji, cost, grants_minutes, limit_max, limit_period:'day'|'week', sort_order}` — `grants_minutes` is optional; when set, marking a redemption of this prize **Delivered** also credits that many minutes to the child (see fulfillment tracking below)
- `challenges` — `{id, child_id, user_id, chore_id, label, target, bonus, currency, type:'recurring'|'onetime', start_date, end_date}`
- `punishments` — `{id, child_id, user_id, label, block_points, block_minutes, block_prizes, ends_at}` — `ends_at` is an absolute ms-epoch timestamp; a punishment is active purely by `Date.now() < ends_at`, no separate lifecycle state
- `entries` — append-only ledger: `{id, child_id, user_id, ts, kind:'chore'|'bonus'|'redeem', ref_id, label, emoji, currency, amount, status:'pending'|'approved'|'denied', fulfilled, minutes_used, grants_minutes}` — the last three power prize fulfillment tracking, see below
- `notifications` — queued Pip moments: `{id, child_id, user_id, kind:'celebration'|'streak'|'goal'|'message'|'comeback', label, emoji, amount, currency, message, ts}` — see "Pip notifications" above. Rows are deleted on delivery, not marked seen; there's no history table.
- `family_settings` — `{user_id, pin}` — the one family/parent PIN; distinct from each child's own `pin` on the `children` row
- `pip_voice_lines` — not per-child: `{id, user_id, category:'opener'|'closer'|'celebration'|'redeem'|'comeback'|'streak', file, phrase}` — `file` is just a filename inside the repo's `voices/` folder (the audio bytes themselves aren't in Supabase at all); see "Pip voice lines" above.

`children`/`chores`/`prizes`/`challenges`/`punishments`/`entries`/`notifications`/`pip_voice_lines` are all realtime-subscribed (`subscribeRealtime()`) — a change from any other kiosk triggers a debounced full refetch (`scheduleRefetch()`). `activeChildId` (which child a given device is currently viewing) is **local-only**, kept per-device in `localStorage`, never synced.

In-memory shape (`app.js`, per child): `{id, name, avatar, pin, points, minutes, weekStart, goalPrizeId, chores[], prizes[], challenges[], punishments[], entries[], notifications[]}` — camelCase (`choreId`, `startDate`, `limitMax`, `blockPoints`, `grantsMinutes`, `minutesUsed`, `sortOrder`, etc.); conversion to/from snake_case DB rows happens in `rowsToChild()` / `insertChildFull()` / `toEntryRow()` / `toNotificationRow()`.

All balance changes flow through `approveEntry(id)` (or the manual-backfill functions in Settings, or `logMinutesUsed()`/`markFulfilled()` for the fulfillment-tracking paths below) — never mutated ad hoc elsewhere. Nothing is deleted from `entries` under normal use; denied requests stay in history with a `denied` status. The one deliberate exception is Settings → Data → "Edit Individual Entries" (`unapproveEntry()` / `deleteEntryPermanently()`), a parent-facing correction tool for an outright mistake, not a routine editing path — see the Settings bullet above and `reverseApprovedEffect()` (right after `denyEntry()`). Every Supabase write ends in `.throwOnError()` — the JS client resolves rather than rejects on API/DB errors by default, so omitting this silently swallows real failures.

**`makeChild()` mints fresh per-child ids for every seeded default chore/prize/challenge** (`uid()`, not the human-readable literal ids like `'dishes'`/`'school'` the `DEFAULT_*` arrays use as source data) — those ids are plain primary keys in Supabase, not composite with `child_id`, so reusing them across children collided the moment a second child was added (`chores_pkey` duplicate). If more seed/default data is ever added, keep minting fresh ids the same way rather than reusing the literal source-data id.

## Prize fulfillment & minutes-usage tracking (`app.js`)

Approving a redemption only deducts points immediately — it doesn't mean the reward actually happened yet. `entries.fulfilled` tracks that separately: `markFulfilled(id)` sets it (from a "claimed, not delivered yet" section in Parent Zone → Approvals), and if the prize has `grants_minutes` set, that's the moment those minutes actually land in the child's balance — not at redemption/approval time.

`minutesGrantTotal(e)` computes how many minutes a given approved entry is worth: `e.amount` for any chore/bonus entry with `currency==='minutes'`, or `e.grantsMinutes` for a fulfilled redeem entry, else 0. `logMinutesUsed(amount)` (Settings → Points & Time → "Log screen time used") drains that amount **oldest-first (FIFO)** across every entry with remaining `minutesGrantTotal(e) - (e.minutesUsed||0)`, splitting across multiple entries if needed, and decrements the child's real minute balance — a labeled, tracked alternative to the blunt +/-5 adjuster.
- `reverseApprovedEffect(c, e)` (Settings → Data → Edit Individual Entries, see above) relies on exactly this bookkeeping to stay correct: it only claws back `minutesGrantTotal(e) - (e.minutesUsed||0)` — the *unused remainder* — not the full original grant, since any already-`logMinutesUsed()`-drained portion was already removed from the balance separately. Reversing the full grant instead would double-count and hand back minutes that were already spent.

## Challenges engine (`app.js`)

`isChallengeActive(ch, dateKey)`, `challengeProgress(child, ch)`, `challengeBonusGranted(child, ch)`, `maybeGrantChallengeBonus(child, ch, status)`, `checkChallengesForApproval(child, entry, status)` — invoked from `approveEntry` and `addPastChore` whenever a `kind:'chore'` entry is approved. A bonus entry's `refId` is the **challenge's own id** (not the underlying chore's), so multiple challenges can independently watch the same activity without colliding. `lastActionSnapshot.extraEntryIds` is an array (not singular) so undo can revert every bonus a single approval may have triggered. The bonus entry created here is `pending`, not auto-approved — it's a normal Approvals-queue item, so the "streak" Pip moment (see "Pip notifications") only fires later, when that bonus entry itself gets approved (`approveEntry` tags a notification `kind:'streak'` specifically because `e.kind==='bonus'`), not at the moment the challenge target is actually reached.

## Punishments engine (`app.js`)

`isPunishmentActive(p)`, `activePunishments(c)`, `isBlocked(c, field)`, `isChoreBlocked(c, chore)` — `requestChore`/`requestPrize` check these before creating an entry and refuse (with a toast) if blocked; this is enforced at the request function, not just visually. `schedulePunishmentExpiry()` sets a one-shot `setTimeout` to the soonest active punishment's `endsAt` so a block visually lifts on its own without the child needing to tap anything, and (see "Pip notifications" above) queues a Comeback Pip moment for the child at the same time. Manually removing a punishment early (Parent Zone → Punishments → Remove) triggers the same Comeback Pip notification.

## Rendering pattern

No framework/virtual DOM. `render()` regenerates the header stats and calls one of `homeHTML()` / `prizesHTML()` / `historyHTML()` based on the global `view`, sets `innerHTML`, then `wireMainContent()` reattaches event listeners by querying `data-*` attributes. The Parent Zone overlay follows the same pattern via `renderParentBody()` / `wireParentBody()`, keyed on `activeParentTab` (`approve` / `chores` / `prizes` / `challenges` / `punishments` / `settings`). Icon/avatar picker, schedule picker, challenge picker, punishment picker, and prize-limit picker are separate overlays that all follow the same draft-state → editor-HTML → wire → save shape (`*PickerContext` / `*Draft` globals). List-edit rows (Activities, Prizes, Challenges, Punishments, the child-rename row) share a common two-line card shape — `.item-row-main` (drag handle + icon + name/primary control + trailing action button(s)) stacked above `.item-row-meta` (secondary controls, wraps via `flex-wrap`) — inside a plain `.list-edit-item` container, which is what keeps these rows from overflowing horizontally on a phone-width screen. Activities and Prizes rows are drag-reorderable via `wireDragReorder()` — a small hand-rolled Pointer Events (not HTML5 Drag and Drop, which iOS Safari doesn't support for touch) engine that reorders the DOM live and persists `sort_order` on drop.

## Working in this repo

- No build/test/lint tooling — edit `index.html`/`app.js` directly. Serving needs a real HTTP origin (not `file://`) for the Supabase CDN script/fetches to work; a small local PowerShell `HttpListener` script is the fallback when Python/Node aren't installed on the machine.
- The app requires a live Supabase connection to get past the login/loading screen — there is no local-only/offline mode. `requireOnline()` gates every mutating action before any local mutation happens.
- Keep new UI consistent with the existing CSS custom-property theme in `index.html` (`--navy`, `--teal`, `--coral`, `--gold`, etc.) rather than introducing new ad hoc colors — except where a Pip-artwork card deliberately pulls its own gradient from that art's palette (see "Pip mascot system" above).
- Schema changes need a manual SQL migration, run by the user in the Supabase SQL editor (no migration tooling exists) — write it additive/backfill-only wherever possible, and hand it over as a file for the user to run themselves rather than executing it. Check for already-existing-but-unused columns first (this happened twice: `prizes.grants_minutes`/`entries.grants_minutes` were leftovers from a previously-removed feature and just needed re-wiring, no migration required).
- User-facing copy says "Activity/Activities"; the underlying code, CSS classes (`.chore-card` etc.), and the `chores` table are still named `chore`/`chores` — that's intentional (a display-only rename), not an inconsistency to "fix" reflexively.
- The app is used both on 10.1in kiosk tablets (portrait/landscape, `@media (min-width:700px)`/`(min-width:1000px)` breakpoints) and on parents' phones for Parent Zone — narrow-width layouts matter, not just tablet ones. A useful local test technique for phone widths: embed `http://localhost:8000/` in an `<iframe>` sized to the target CSS pixel dimensions (e.g. 393×852 for iPhone 15) rather than relying on browser window resize, which doesn't reliably affect the viewport in this environment.
- Bump `CACHE_NAME` in `sw.js` on every shipped change.
- For destructive-looking test scenarios (a second child, a punishment, a redemption), prefer creating disposable test data (a throwaway child, injected in-memory notifications/punishments) and cleaning it up afterward over mutating the user's real children's real balances/history — this has come up repeatedly since the user's real kids' data lives in the same Supabase project used for testing.
